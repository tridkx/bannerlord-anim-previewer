# 技术记录

实现这个预览器时**实测**出来的结论、踩过的坑、以及"怎么判断对不对"的方法。
都是可以独立复核的，改动相关代码前建议先读一遍。

---

## 1. 数据格式结论（全部用真实数据验证过）

### 1.1 骨架

`mbtool skeljson` 导出的 `rest` 是 **4×4 列主序**矩阵，其中：

* 平移列是**相对父骨的偏移**，且表达在**父骨局部坐标系**里
* 世界矩阵 = 父世界 @ 本骨 rest（标准层次相乘，不需要任何额外轴变换）

**自检判据**（数值不对就是骨架选错或矩阵约定错了）：

```
脚趾 z ≈ 0（踩地）    头 z ≈ 1.57    左右手 |x| 近似相等
```

实测 `bip01_notused`：骨盆 0.9145 / 头 1.5699 / 脚趾 −0.004 与 +0.0006。

`skeletons.tpac` 里有**多个同名骨架**（不同 GUID），实测 rest 完全一致，取第一个即可。

### 1.2 动画四元数的语义

有一个判别实验，结论很干脆：

| 假设 | 与 bind pose 的旋转偏差 |
|---|---|
| `q` 是世界绝对朝向 | 83°~180° ✗ |
| **`q` 是相对父骨的局部旋转** | **0°~12°** ✓ |

判据是"沿链复合后与 bind 世界旋转的夹角"。**第一帧即接近绑定姿势**，
偏差那几度是待机姿势与绑定姿势的正常差异。

### 1.3 姿态公式

```
M_i(t) = M_parent(t) · [ R(q_i(t)) | restLocal_i.translation ]
根骨额外叠加 rootPosition 平移（每帧 3 个 float）
蒙皮矩阵 = M_pose @ inv(M_bind)
```

不需要坐标轴变换矩阵、不需要求增量、不需要特殊处理根骨以外的平移
—— **每根骨只有旋转**，平移全部来自骨架 rest。

**验收数值**（正确实现的水平）：

| 项 | 实测 |
|---|---|
| 站立时脚底 z | ≈ 0.002 |
| 头高 | 1.556 ~ 1.569 |
| 走路时左右踝 y | 交替 ±0.4m（−0.475/+0.278 → +0.307/−0.293）|
| 走路抬脚 | 27cm |
| 手臂 | 从 A-pose 的 x=0.650 收回到自然摆臂 x=0.26~0.34 |

### 1.4 ★ 蒙皮矩阵的乘序（一个只在动起来时才暴露的坑）

```
正确:  skin_i = M_pose_i @ inv(M_bind_i)
写反:  skin_i = inv(M_bind_i) @ M_pose_i      → 顶点被甩到 2 米外
```

**为什么极难发现**：bind pose 下 `M_pose == M_bind`，两种写法**都退化成单位阵**，
于是所有"t=0 自检"全绿、顶点偏差只有 0.0002mm。
**只有 t>0 的帧才会露馅**（实测最大顶点位移 2042mm、边长比 12.5 倍）。

> **蒙皮类验证一律用 t>0 的帧。t=0 的自检是平凡检验。**

### 1.5 UV 的 V 轴：用统计判据定，别靠经验

本源是 **top-origin**，而 WebGL 的 `glTexImage2D` 第一行数据正好落在 `t=0` ⇒ **不翻**。

判据（对角色贴图特别有效，因为大片是 alpha=0 的空白区）：

```
统计"UV 采样落在贴图不透明区的顶点占比"：
  不翻 V → 89.6%       翻 V → 4.3%      ⇒ 不翻
```

实测 `ying_skin_d` 只有 11.8% 的像素不透明，所以 V 轴错了会立刻掉到个位数。

⚠️ Blender 侧结论相反（Blender 的 v=0 在图片底部），**两边不能互抄**。

### 1.6 装备遮盖

Bannerlord 的角色不是整体网格，而是「原版皮肤部件 + 若干装备件」按槽位拼起来的。
`covers_body` / `covers_hands` / `covers_legs` / `covers_head` **不参与渲染**，
而是被反序列化成 `MeshesMask`，由原生代码决定隐藏哪些原版皮肤网格。

原版部件定义在 `Modules/Native/ModuleData/skins.xml`：

| 字段 | 用途 |
|---|---|
| `body_meta_mesh` / `body_meta_mesh_shoulders` | 躯干 / 肩 |
| `legs_mesh` / `hands_mesh` / `face_meta_mesh` | 脚 / 手 / 头脸 |
| `underwear_bottom_mesh` / `underwear_top_mesh` | 内衣 |

全部在 `Modules/Native/EmAssetPackages/human/human.tpac`（17 个 metamesh、16MB，
导出只要 0.22 秒 ⇒ 全量导出即可）。身体材质跨包在 `mat1/body_materials/`。

**两个必须做对的细节**：

1. **`covers_*` 是按语义（body/hands/…）遮的，不是按网格名。**
   拿网格名 `body_male_a` 当 key 去匹配 `hidden.has('body')` 永远匹配不上 ——
   表现是"原版身体永远露着"或"永远不露"。
2. **只加载当前体型用到的那几个网格。** human.tpac 里 male/female/kid 全都有，
   全量加载会让**男女两具身体同时出现**。

**验收**：装备前后绘制数明显变化（实测 41 → 19）；只留一件装备（如只穿鞋）时，
必须能看到原版身体大面积露出来。

### 1.7 播放速率：三个坑叠在一起

```
播放速率 = 有效跨度 / AnimationClip.duration
```

**坑一：不能用 `animlist` 的 `dur` 字段当帧数。**
`SkeletalAnimation.duration` 与实际关键帧范围**不一致**：实测 `inventory_idle`
是「字段 630 / 实际 1267 帧 / clip 15s」。拿它算会慢整整一倍；
`stand_non_combat` 差 4 倍。

**坑二：★★ 所有动画的第 0 帧是绑定姿势（A-pose），不是动画内容。**

| 动画 | 帧 0 | 帧 1 | 跳变 |
|---|---|---|---|
| `inventory_idle` | 手 z=1.107（A-pose） | 手 z=0.895（待机垂手） | **162°** |
| `walk_forward_unarmed` | 手 z=1.106 | 手 z=0.879 | **67°** |

算进播放范围的话，**每循环一次角色就闪一下 A-pose**，观感上就是"节奏不对/像是倍速"。
自动识别判据（`baker/animation.py`）：

```
jump = 骨骼最大夹角(帧0, 帧1)
rest = median(骨骼最大夹角(帧i, 帧i+1))  for i in 1..60
若 jump > 45° 且 jump > 3×rest  ⇒  真正的起点是帧 1
```

**坑三：同一动画常被多个 clip 引用，`duration` 未必相同**（实测 550 个动画如此）。
盲取第一个会让速度差整数倍。打分规则：clip 名 == 动画名 > 带 `cyclic` > 名字是前缀关系。

最终实现：`span = (frames-1) - start`，`rate = span / clip_duration`。
实测 `inventory_idle` 1266/15.0 = **84.4**、`walk` 36/1.4 = 25.7、`run` 24/0.8 = 30.0。

> `rate` 是"把动画铺满 clip 时长"的比例，**不是引擎帧率**。
> 而且观感仍可能与游戏不同（游戏可能另有播放倍率），
> 所以界面必须提供**可调倍速**并记住选择，不要替使用者认定"绝对正确"。

## 2. 判据的选择（比结论更值钱）

排查过程中用过的判据，**前三个都有致命盲区**：

| 判据 | 盲区 |
|---|---|
| 关节位置（两腿在 X 分开、脚在地上、头最高） | 用 `abs()` 取间距就**看不出左右翻转**；且完全不看旋转 |
| 父子骨**相对旋转**偏差 | **旋转角是相似不变量** ⇒ 对坐标变换完全不敏感 |
| 顶点**位移大小** | 角色真转身 32° 本来就会产生几百 mm 位移，**大 ≠ 错** |
| ★ **网格边长/三角形拉伸** | **唯一真正硬的判据**：LBS 是刚体变换的凸组合，正确约定下只会平滑变化，不会出现几十倍尖刺 |

**两条配套的校准**（不加会误报）：

* **只看 >1cm 的边**。毫米级短边在权重过渡区本就会被相对拉伸 ——
  实测把 2.4mm 的边算出了 12.5 倍"拉伸"，其实绝对位移只有 3cm。
* **位移要用离群度，不能用绝对值**。`jump` 这类单帧姿势动画与 bind pose
  差异本来就大（实测 p99 就有 2.21m），必须判 `max > 1m 且 > 6×p99`。

## 3. 怎么判断"渲染到底对不对"

**别盯着整体画面猜，做逐层对比。** 本项目实际用过的完整手法：

1. **`--only <材质>` 逐层渲染** —— 把每个材质单独出一张图。
   实测 `ying_cloth` 单独渲染完全干净（衣服颜色全对），说明"肩膀发黑"不是它造成的。
2. **`--no-alpha-test`** —— 关掉镂空，看被 discard 的部分长什么样。
   实测关掉后深灰**依旧存在** ⇒ 与 alphaTest 无关，立刻排除一个方向。
3. **像素 diff** —— 两版渲染结果求差，量"差异像素占比 + 差异区域颜色"。
   实测只有 0.09% 差异，且颜色是"背景 → 肤色" ⇒ 叠加是正确的，没有 bug。
4. **`--debug 1` 仅贴图** —— 排除光照。

**结论**：那次"肩膀深灰"最终确认是 `ying_cloth_d` 贴图在该 UV 区域的真实颜色
（各材质单独渲染都正常），**不是渲染错误**。没做逐层对比的话，很容易误改渲染代码。

## 3.5 ★★ `alpha_test` 材质必须走 Cutout，不能按半透明混合

`blendMode` 是 `factor` 且 `shaderMatFlags` 含 `alpha_test` 的材质（实测原版有 340 个，
包括**人发** `hair_male_c`、胡子 `beards_h` 与大量植被），正确处理是
**alpha 只用来 discard、留下的像素当实心**，而不是再做一次 `SRC_ALPHA` 混合。

判据（实测贴图的 alpha 分布）：

| 贴图 | alpha<0.275（丢弃） | 半透明 | 完全不透明 |
|---|---|---|---|
| `yx_hair_d`（显示正常的那件） | 0% | 0% | **100%** |
| `bai_hair_d` | 58% | 9.7% | 32% |
| `pl1270_preps_hair_d` | 68% | **29.5%** | 仅 **2.3%** |

最后一行是关键：**只有 2.3% 的像素完全不透明**，按 `SRC_ALPHA` 混合整头头发都会发虚。
而 `alpha_test` 的语义本就是"二值化 alpha"，所以 Cutout 才是对的。

实现：`blend = !alphaTestOn && blendMode !== 'no_alpha_blend'`，
片元着色器在 discard 之后输出 `alpha = 1.0`。
诊断开关：`?blendtest=1` 可以切回半透明混合做对比。

## 3.6 ★★ 原版身体部件显示成纯白（"戴了白手套"）

没被装备 `covers_*` 盖住的原版手/身体会露出来 —— 这是期望行为。但它们**显示成纯白**，
看着像戴了一副白手套。两个原因叠在一起：

**一、human.tpac 里的网格材质名是空的。**
Bannerlord 把身体网格和它的材质**分在两个包里**（网格在
`EmAssetPackages/human/`，材质在 `mat1/body_materials/`），
`exportmod` 导出单个包时本包内查不到材质名，于是是空串，回退成"无材质的白图"。
⇒ 用 `pack.json` 里的 `materialGuid` 关联回来（实测 21/22 命中）。

**二、原版身体材质在 tpac 里一个贴图都没有。**
`body_materials.tpac` 的 50 个材质（`body_male_a` / `head_female_a` / `eye_mat` …）
`textures` 全是空的 —— 因为游戏是**运行时按肤色/体型程序生成**的，磁盘上根本不存在。
⇒ 按材质类别生成兜底纯色：

| 类别 | 判据（材质名） | 颜色 |
|---|---|---|
| 皮肤 | `body_*` / `head_*` / `*_skin` | (206,160,128) |
| 头发 | 含 `hair` | (58,44,36) |
| 胡子 | 含 `beard`（`beard_skin` 除外） | (74,58,48) |
| 眼白 | 含 `eye` | (196,192,188) |
| 唇 | 含 `mouth` | (168,106,98) |
| 眉 | 含 `brow` | (86,64,52) |
| 内衣 | 含 `underwear` | (214,210,204) |

**两个坑**：

* **不能一刀切全涂肤色** —— 会把 `eye_mat` 也涂掉，角色看起来像没长眼睛。必须按类别。
* **只给真正用在身体部件上的材质挂** —— 从导出结果里收集实际用到的材质名，
  否则会波及无关材质。

> 兜底色是**预览用的中性近似**，不是游戏里读出来的真实肤色
> （肤色由角色创建时的 `BodyProperties` 决定，tpac 里没有这个信息）。
> 对"看自己的装备"这个用途够用；原版身体只是参照物，也可以直接关掉显示。

## 3.7 ★★ `covers_hands` 的语义：**隐藏原版手**，不是"提供手"

排查"游戏里看不到手"时踩到的坑，务必记牢方向。

**证据链**：

1. `TaleWorlds.Core.dll` 里 `covers_hands` 与 `MeshesMask` / `SkinMask` 相邻，
   `TaleWorlds.MountAndBlade.dll` 里有 `GetSkinMeshesMask()` ——
   这条链的产物是**要隐藏哪些原版皮肤网格**的掩码。
2. 原版数据分布（v1.4.8）：
   | 文件 | 件数 | 用了 `covers_hands` 的 |
   |---|---|---|
   | `body_armors.xml` | 246 | **0** |
   | `arm_armors.xml` | 35 | 16 |
   | `leg_armors.xml` | 39 | 0（只用 `covers_legs`）|
   | `head_armors.xml` | 256 | 0 |
   即 `covers_hands` 是**手部装备专用**的，从不用在身甲上。
3. 预览器实测（天香套，只改 `tianxianyifu` 一个字段）：

   | | 绘制数 | 手 |
   |---|---|---|
   | `covers_hands="true"` | 13 | **消失** |
   | 不设 | 14 | **显示** |

   **差值正好是那一个原版手网格。**

**结论**：想让手**显示**，就不要给身甲加 `covers_hands`；
该字段表示"这件装备自己带手，把原版手藏掉"，
所以只有**网格里真的含手**的手套才该设它。

**给身甲加 `covers_hands="true"` 而身甲又没有手部几何 ⇒ 手彻底消失。**

## 3.8 判断"某个部位是 mod 提供的还是原版的"

靠坐标猜不可靠（绑定姿势未必是标准 A-pose）。**看骨骼权重**：

```python
# 主骨分布：每个顶点取权重最大的那根骨
main = bi[np.arange(len(bi))[:, None], np.argsort(-bw, axis=1)[:, :1]].ravel()
```

实测（LVBU and DIAOCHAN）：

| 网格 | 前臂末端骨顶点 | 手骨顶点 | 判定 |
|---|---|---|---|
| `diaochanshou`（貂蝉手套） | 1403 / 1403 | 0 | ✓ 整只手套 |
| `xinzhenjiyifu`（新真姬衣） | **3940** | 0 | ✓ 身甲**确实**带手 |
| `kehanyifu`（可汗衣） | 1770 | 0 | ✓ 身甲带手 |
| `tianxianyifu`（天香衣） | **106** | 0 | ✗ 只有袖口 |

**注意**：这个 mod 的手套把顶点绑在**前臂末端骨**（`*_foretwist1`，索引 18/25），
不是手骨（19/20/26/27）—— 所以**手骨权重为 0 不代表没有手**，
必须同时看前臂末端骨。只查手骨会误判。

## 3.9 ★★★ 穿身甲后"手消失"：自定义种族的手长在身体网格上

排查"游戏里 LVBU 装备的角色看不到手"的最终结论。**与游戏版本无关**，
是**自定义种族的 skins.xml 结构**造成的。

**关键字段**（`ModuleData/skins.xml` 的 `<skin>`）：

| skin | skeleton | body_meta_mesh | hands_mesh |
|---|---|---|---|
| `man`（原版 human） | `human_skeleton` | `body_male_a` | **`hands_male_a`** |
| `jingrenou`（JingRenOuRace） | `jingrenou_skeleton` | `jingrenou` | **`""` 空** |
| `valerie`（ValerieRace） | `valerie_skeleton` | `valerie_body` | **`""` 空** |

**网格实际引用了哪些骨**（`bones referenced`）才是判据：

| 网格 | 引用的骨 | 含手骨 19/26 |
|---|---|---|
| 原版 `body_male_a`（躯干） | `[0..18,21..25]` | **✗ 不含** |
| 原版 `hands_male_a`（手） | `[0,16,17,18,19,23,24,25,26]` | ✓ |
| `jingrenou`（种族身体） | `[…,19,…,26]` | **✓ 含** |
| `valerie_body` | `[…,19,…,26]` | **✓ 含** |

**因果链**：

1. 自定义种族**没有独立的手部网格**，手**长在 `body_meta_mesh` 上**；
2. 身甲 `covers_body="true"` ⇒ 游戏隐藏 `body_meta_mesh`；
3. 手**跟着身体一起被隐藏** ⇒ 角色没手。

人类角色不受影响：躯干网格**不含手骨**，手是独立的 `hands_male_a`，
`covers_body` 隐藏躯干时手照常显示。

这也解释了为什么"**独立的手套/护腕还在，手掌却没了**" ——
手套是独立网格不受影响，手掌长在身体上被一起隐藏。

**两个解决方向**：
- 用**人类角色**（帝国文化）穿这套装备 —— 立刻正常；
- 给种族 mod 拆出**独立的手部网格**，`skins.xml` 里把 `hands_mesh` 指向它。

## 4. 光照：量必须配平到 ≈1.0

```
颜色 = 贴图 × (环境光 + 直射光·N·L) + 高光
```

实测**环境 + 直射总量只有 0.55** 时，浅肤色贴图被压成**灰蓝色** ——
看起来像"贴图错了"，而切到 `--debug 1` 仅贴图模式又完全正常，极易误判。
反过来总量 >1 会把深色贴图抬成灰白。

光照参数可以直接从游戏大气 XML 取（**装备页场景**）：
`Modules/Native/Atmospheres/item_scene_atmosphere.xml`

```
sun_altitude=70   sun_intesity=0.700   sun_color=1.000,0.932,0.891
global_ambient fog_ambient_color=0.517,0.708,1.000    env_map=mp_ruins_2_envmap
```

游戏另有延迟渲染管线与后处理（曝光 −4EV、bloom、SSAO），本项目**不移植**这部分 ——
**明暗关系接近，但不等于实机截图**。

## 5. 踩坑清单

### 5.1 渲染 / 数据

| 坑 | 症状 | 做法 |
|---|---|---|
| **GDMB 索引是 i32** | 当成 u16 读会让后续解析整体错位、报"残留 N 字节" | 每个索引 4 字节 |
| **MBMG 的 JSON 块未 4 字节对齐** | `new Float32Array(buf, off, n)` 因 `byteOffset` 不是 4 的倍数抛错 | 用**空格**补齐（空格是合法 JSON 尾部空白，比补 `\0` 安全） |
| **错误层 appendChild 无限堆叠** | 切到加载失败的动画 → 全屏错误层永久盖住角色，反复触发表现为"角色忽隐忽现" | 错误面板**复用同一个 DOM 并给关闭按钮**；单个资源失败只弹 toast，不要 fatal |
| **贴图请求无超时** | `onload`/`onerror` 都不触发时 `await` 永久挂起 ⇒ 加载遮罩永不消失 | 给图片加载加 `setTimeout` 兜底 |
| **`fatal()` 之后 `setLoading(false)` 不执行** | 抛异常导致加载遮罩留在屏幕上 | 遮罩开关放 `finally` 或外层 catch |
| **resize 到 0 尺寸** | 面板折叠瞬间量到 0，把画布设成 1×1 ⇒ 画面"消失" | 小于阈值就不重设画布 |

### 5.2 WebGL

| 坑 | 症状 | 做法 |
|---|---|---|
| **骨骼 uniform 数组开太大** | `mat4[64]` = 256 个 vec4，正好顶到 `MAX_VERTEX_UNIFORM_VECTORS` 的最低保证值；弱显卡链接失败后 `getUniformLocation` 返回 null、uniform 上传被**静默忽略** | 按骨架实际需要开（人形固定 28）；上传前判 null |
| **`preserveDrawingBuffer`** | 部分驱动上与抗锯齿打架导致闪烁 | 除非真需要读回像素，否则关掉 |
| **镂空边缘闪烁** | alpha 在阈值附近时 mipmap 采样让它逐帧时有时无 | 对 alphaTest 材质启用 `SAMPLE_ALPHA_TO_COVERAGE` |
| **NaN 传播** | frame 变成 NaN ⇒ 整具骨架矩阵 NaN ⇒ 角色整个消失 | 进 `Rig.update` 前兜住；`setBones` 里再兜一层 |

### 5.3 工具链 / 环境

| 坑 | 症状 | 做法 |
|---|---|---|
| **.bat 里的 UTF-8 中文注释** | 控制台代码页是 GBK ⇒ 字节错位 ⇒ 可能吐出 `&` `\|` `>` 被当命令分隔符，报 `'疆' 不是内部或外部命令` | **bat 一律纯 ASCII**，中文提示交给 Python 输出 |
| **Python 输出被缓冲** | 后台跑时 `print` 的内容丢失 | 用 `python -u`，或 `flush=True` |
| **`np.frombuffer` 只读** | 直接改会报错 | 需要写就 `.copy()` |
| **GBK 控制台** | 打印中文/`²` 直接 `UnicodeEncodeError` | 脚本开头 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` |

### 5.4 ★★ 改完 mod 预览没变化 —— 「有缓存，但缓存不校验新鲜度」

**症状**：重新打包并安装 mod 后，打开预览器看到的还是旧模型；刷新页面也没用。

**根因分三层，别混为一谈**（这点很容易说错）：

| 层 | 有没有缓存 | 缓存的是什么 |
|---|---|---|
| `bake_mod()` 烘焙层 | **没有新鲜度判定**（每次全量重导出） | — |
| HTTP 层 | 已禁用（`Cache-Control: no-store`） | — |
| **触发层** | **有，且只看「文件存不存在」** | `data/mods/<mod>/manifest.json` |

- **烘焙层是无辜的**：`bake_mod()` 不比对 mtime，`MB.exportmod()` 每次都重跑，所以**只要调用就必然产出新数据**。
  （对比同文件的 `ensure_skeleton` / `ensure_catalog` / `ensure_vanilla`——那三个才有 `_fresh()` 判断，且缓存的都是**原版游戏资产**，与 mod 无关。）
- **真正的问题在触发层**：`baked` 的判据就是 `manifest.json` 存不存在（`server.py`），
  前端只在 `loadManifest()` **抛 404 时**才去查 `baked`，且**只有 `!baked` 才触发烘焙**。
  所以 mod 更新 → `manifest.json` 依然存在 → `baked=true` → 永远不重烘 → 旧产物。

**决定性判据**：如果这个缓存带新鲜度校验，mod 更新后应当自动重烘（表现为「更新后反而变慢几秒」）。
**观察不到这个行为，本身就是缓存不校验新鲜度的证据。**

**做法**：改完 mod 显式重烘，不要只刷新页面。
界面顶部 mod 下拉框旁的「**重烘焙**」按钮即为此设；命令行等价物是 `mbpreview.bat bake <mod>`
（不加 `--force` 也会全量重导出；`--force` 额外先清空 `geo/` `tex/`，用于回收残留文件）。

> ⚠️ **前端还有第二层缓存**：`loader.meshCache / texCache / animCache` 是 JS 侧按相对路径做键的 Map。
> `no-store` 只管网络，管不到这几个 Map——重载时路径一字不变，不清空就永远命中旧对象。
> 所以任何"就地重载"都必须先 `clearLoaderCaches()`，否则按钮点了没反应。

**副作用**：mod 改名或删除网格后，旧的 `.mbmg` / `.png` 会残留在 `geo/` `tex/`。
不影响正确性（`manifest.json` 重写且只引用本次导出的条目），但白占磁盘、同名时有读到旧文件的风险。
彻底重建（`--force` / Shift+点击）可清掉。

## 6. 与上一版预览器的差异

上一版在 `D:\mb-tools\preview\`（已移除），其记录不再保留。关键差异：

| | 旧版 | 本项目 |
|---|---|---|
